# Internals deep-dive

A more detailed walk-through of the trickier decisions, for readers who
want to understand *why* and not just *what*. Pair with
[ARCHITECTURE.md](ARCHITECTURE.md), which explains the layers.

## Chunking: why 9 MiB?

Discord caps free attachments at **10 MB**. AES-GCM ciphertext is the
same length as plaintext, plus a 16-byte authentication tag and a
12-byte nonce. The nonce travels alongside in the inode JSON, not
appended to the ciphertext, so:

```
plaintext_size + 16  ≤  10 * 1024 * 1024
plaintext_size       ≤  10,485,744 bytes
```

We pick **9 MiB = 9,437,184 bytes** as the target plaintext chunk size,
leaving ~1.05 MiB of headroom for future metadata growth, multipart
form overhead, and ad-hoc safety margin.

### Why not content-defined chunking (FastCDC)?

[FastCDC](https://github.com/nlfiedler/fastcdc-rs) is the standard
library for content-defined chunking in Rust. CDC matters when you
want **deduplication** — if you have two large files differing only
in a small section, CDC produces overlapping chunk boundaries so you
can store the shared part once.

Two problems for us:

1. **CDC has hard size caps.** The crate constrains:
   - min_size ≤ 1 MiB
   - avg_size ≤ 4 MiB
   - max_size ≤ 16 MiB

   Our target avg ≈ 9 MiB is over both `avg_size` and inside the
   `max_size` window, so we can't pick boundaries inside the 4–16 MiB
   range cleanly. (Yes, we could call CDC at 4 MiB avg and pack two
   chunks per Discord message, but that doubles message count.)

2. **The dedup payoff is small** for our likely use case (single user,
   personal files). Unless you're storing many large VM images with
   shared OS layouts, fixed-size chunking gives the same wire cost.

So we have **fixed-size 9 MiB chunks** with no deduplication. The
chunker is 12 lines.

### What you give up

- No dedup. Two identical files double the storage cost.
- Slightly worse compressibility for end-aligned binary content.
- No content-aware boundary stability across edits — a one-byte
  insert near the start re-uploads every chunk.

In exchange you get: zero CDC bugs, zero cipher/hash subtleties around
variable-size chunks, and a chunker that fits in your head.

## Cipher choice: AES-256-GCM

We use `aes-gcm = "0.10"` with the `Aes256Gcm` profile (256-bit keys,
128-bit GCM tag).

### Why AES-GCM and not, say, XChaCha20-Poly1305?

- **GCM has hardware acceleration** on every modern x86_64 CPU via
  AES-NI. ChaCha is the right pick on machines without it — but
  WinFSP-running Windows boxes almost always have AES-NI.
- **GCM is the most widely-reviewed AEAD** with first-class library
  support, audit history, and clear test vectors.
- **96-bit nonces** are the right size for `rand::thread_rng()`. We
  generate one per chunk; chance of collision over 2^48 chunks per key
  is negligible.

### Nonce management

Each chunk gets an independent 96-bit random nonce, stored in the
inode `ChunkRef`. Note we do **not** derive nonces from a counter or
the chunk index — random nonces are simpler and sufficient given
we're well below GCM's 2^32 nonce-reuse threshold for any realistic
key lifetime.

Key derivation isn't fancy: the master key is 32 random bytes
generated by `rand::thread_rng().fill_bytes()` at init and used
directly. There's no per-file or per-directory subkey because we
don't need separable trust domains.

### Why hash plaintext, not ciphertext?

The `ChunkRef::sha256` field stores SHA-256 of the **plaintext**, not
the ciphertext. Three reasons:

1. **Deduplication-by-hash works on plaintext.** (We don't dedup
   today, but the option stays open.)
2. **GCM tag failure already authenticates the ciphertext** — if a
   ciphertext byte flips, GCM's `decrypt` rejects. So hashing the
   ciphertext too would be redundant.
3. **Detect tampering with the inode itself.** If someone edits the
   `nonce` field in our inode to attack us, decrypt with the wrong
   nonce produces garbage plaintext whose SHA won't match — we catch
   it.

Concrete check on read:

```rust
let plain = aes_gcm.decrypt(nonce, ciphertext)?;
let actual_sha = sha256(&plain);
if actual_sha != chunk_ref.sha256 {
    return Err(Error::IntegrityFailure(hex::encode(chunk_ref.sha256)));
}
```

If anything in the path — Discord, network, our cache, the disk —
corrupts a byte, this catches it. We've burned it into the test suite.

## Sharding by SHA prefix

We pick a data channel for a chunk like this:

```rust
let idx = u32::from_be_bytes([sha[0], sha[1], sha[2], sha[3]]) as usize
        % data_channels.len();
let channel = data_channels[idx];
```

The first 4 bytes of SHA-256 give us 32 bits of (effectively) uniform
random distribution. For 4 channels you get ~25% of chunks each ±
sampling noise.

### Why this and not round-robin?

A round-robin counter wouldn't survive process restarts cleanly. By
deriving the shard from content hash, the **same chunk always lands in
the same channel** — which makes resharding (e.g. growing from 4 to 8
data channels) deterministic if we ever need to.

It also helps if we ever do content-addressed dedup: identical chunks
go to identical (channel, msg_id) pairs.

### Why exactly 4 channels?

Empirically:
- Discord rate-limits text channels at ~5 messages per 5 seconds per
  channel for a normal bot.
- Larger files = more chunks; spreading across 4 channels gives you
  ~4 chunks/sec sustained, which is roughly the bandwidth budget your
  home upload can sustain anyway.
- More channels would help marginal throughput but increases ToS risk
  ("why is your bot creating 32 channels?").

4 was the sweet spot. The number is configurable, just not exposed
in the wizard.

## Root-pointer pattern (and what's missing)

We chose to keep all server state on Discord, with no local index.
That means we need atomicity primitives we don't have:

- Discord has no transactions
- Discord has no CAS
- Discord has no per-message version numbers we control

Our compromise: **only one message is ever mutable per operation** —
the parent directory we're editing. Everything else (chunks, file
inodes, even the root pointer) is either content-addressed (chunks) or
written-once-then-pointed-at (file inodes).

The root pointer message itself is also mutable, but we only edit it
during `init` (once) and... actually, we don't edit it after init.
The root inode's `message_id` is stable; we edit the root *inode*
message, not the pointer.

### What real production would do

A more battle-tested implementation would:

1. Add a `generation: u64` to the root pointer.
2. Before edit, fetch current generation.
3. After edit, atomically write the new generation only if it still
   matches expected. (Discord doesn't support this directly, so you'd
   layer optimistic concurrency on top via message-edit timestamps and
   conflict detection.)
4. On conflict, retry from step 2.

We don't, because this is a single-user toy. If two GUI instances are
running and both write, the second one's view will be stale.

## The local cache

`src/cache.rs` is two file-based KV stores:

```
%APPDATA%\oubliette\cache\
├── inodes\
│   └── <msg_id>.json     (file inodes only — never directories)
└── chunks\
    └── <sha-hex>.bin     (decrypted plaintext, not ciphertext)
```

### Why decrypted plaintext?

The cache stores plaintext rather than ciphertext. Trade-off:

- **Plaintext caching** is faster on read (no decrypt on hit). But
  if your local disk is compromised, the attacker gets cleartext.
- **Ciphertext caching** is slower (decrypt on every hit) but pushes
  the trust boundary out by one layer.

For a single-user dev tool we picked plaintext. The threat model is
"someone steals my disk image" — at which point they also have my
config.toml with the master key, so plaintext-in-cache buys them
nothing extra.

### Atomic writes

Every cache write goes through `write_atomic`:

```rust
fn write_atomic(target: &Path, data: &[u8]) -> Result<()> {
    let tmp = target.with_extension("tmp");
    std::fs::write(&tmp, data)?;
    std::fs::rename(&tmp, target)?;
    Ok(())
}
```

Rename is atomic on NTFS. Worst case after a crash: a `.tmp` file
remains, which we ignore. We never see half-written cache entries.

## Multi-message-attachment inodes

Most file inodes are small (a few hundred bytes for a 1-chunk file).
Some are large (1000+ chunks = ~150 KB of JSON). The 2 000-char text
limit on Discord messages bites us at ~6 chunks per file inode.

So `Store::post_inode` falls back to **attaching the JSON**:

```rust
async fn post_inode(&self, inode: &Inode) -> Result<MessageId> {
    let json = serde_json::to_string(inode)?;
    if json.len() <= INODE_INLINE_LIMIT {
        self.disc.post_text(metadata_channel, json).await
    } else {
        self.disc.upload_chunk(metadata_channel, "inode.json", json.into_bytes()).await
    }
}
```

Reads (`fetch_message_body`) handle both transparently — if the
message has an attachment, fetch the attachment; otherwise return
the text content.

The same trick *could* apply to directories, but doesn't today —
directories have to be edited in place, and Discord doesn't let you
edit attachments. So directories are capped at the inline limit.
Multi-message directories are on the roadmap.

## Parallelism

We use `futures::stream::buffer_unordered(N)` for parallel chunk
uploads (out-of-order) and `futures::stream::buffered(N)` for parallel
downloads (preserves order so we can stream-write to disk).

```rust
let chunk_results: Vec<(usize, ChunkRef)> = stream::iter(chunk_specs.into_iter().enumerate())
    .map(|(i, spec)| async move { /* read, encrypt, upload */ })
    .buffer_unordered(UPLOAD_PARALLELISM)
    .try_collect()
    .await?;
```

`UPLOAD_PARALLELISM = 4` is a constant — chosen to match the data
channel count. With 4 parallel uploads and SHA-prefix sharding,
chunks roughly spread evenly across the 4 channels, so the
per-channel rate limit governs rather than the global limit.

If you bumped it to 8, you'd see the same chunks queue per-channel
inside serenity's rate limiter; throughput wouldn't improve much.

## Mount-thread teardown

When you click "Unmount" in the GUI, the worker thread needs to
gracefully stop the WinFSP dispatcher. The sequence:

```
[main thread]                  [mount worker]
     |                              |
     |  stop_tx.send(())            |
     |----------------------------->|  rx.recv() returns
     |                              |  host.stop()
     |                              |  host.unmount()
     |                              |  status.ended = true
     |                              |  ctx.request_repaint()
     |  (next update poll)          |  thread exits
     |  sees status.ended,          |
     |  drops MountState            |
     |  (calls join() which         |
     |   returns immediately)       |
```

Two channels of communication:
- `mpsc::Sender<()>` for the stop signal (main → worker, one-shot)
- `Arc<Mutex<MountStatus>>` for status (worker → main, repeated)

The worker thread *owns* the `FileSystemHost` (which is `!Send` due
to internal `NonNull` pointers). The host is dropped on the worker
thread, which runs WinFSP's destructor on the right thread.

## Testing notes

The current test approach is **manual + ad-hoc**:

- Round-trip tests with various file sizes (1 MB, 5 MB, 25 MB, 50 MB,
  100 MB) verifying SHA-256 matches end-to-end.
- Multi-chunk tests verifying parallel uploads & ordered downloads.
- Mount/copy-in/unmount/remount/copy-out cycles for write durability.
- Rename + move + delete via PowerShell on the mounted drive.

What's missing for a real test suite:

- **Unit tests** for chunker, crypto, inode (de)serialization, path
  parsing. These are easy to add — pure functions, no IO.
- **Property tests** for round-trip correctness (with `proptest` on
  random file contents).
- **Discord-mock integration tests** — a fake Discord HTTP server
  that the suite spins up and points the bot at.
- **Concurrent-access tests** — two writers racing on the same
  directory.

PRs welcome on any of these.

## ToS-adjacent design notes

A few things we did/didn't do specifically because of ToS sensitivity:

- **No public bot.** We can't host a bot that thousands of strangers
  invite — both because that scales the ToS issue and because anyone
  could see other users' chunk metadata.
- **No bulk operations.** No batch-upload of an entire hard drive, no
  rsync mode, no syncing. The wizard's friction is intentional.
- **No public chunk URLs.** Even though chunk attachments have CDN
  URLs that briefly work, we always re-resolve them via the message
  API. (Discord made attachment URLs signed in 2024, so this matters
  less now.)
- **Volume-info reports 1 TiB free.** We don't have a real free-space
  metric (Discord doesn't give us one), so we lie consistently. This
  also discourages tools that pre-check free space before bulk copy.
- **Wizard tells you to use a private server.** Loudly. Repeatedly.

This is the part of the project that's most "educational" — a tour
of how to be a responsible adversarial user of someone else's
infrastructure, while still building something interesting.

## Further reading

If this is the first time you've thought about this category of
system, I'd recommend, in roughly this order:

1. [restic's design docs](https://restic.readthedocs.io/en/stable/100_references.html#design)
   — how an actual production chunked encrypted backup tool works
2. [git's pack-file format](https://git-scm.com/docs/pack-format) —
   the original blueprint for content-addressed storage
3. [The FastCDC paper](https://www.usenix.org/system/files/conference/atc16/atc16-paper-xia.pdf)
   — why content-defined chunking exists
4. [WinFSP's tutorial](https://winfsp.dev/doc/Native-API-Tutorial/) —
   how to write a real filesystem
5. [The Discord API reference](https://discord.com/developers/docs) —
   what you're working with (and against)

Reading all five gives you the intellectual foundation for
re-implementing oubliette from scratch in any language.
